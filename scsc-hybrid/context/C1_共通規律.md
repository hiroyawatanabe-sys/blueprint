# C1｜共通規律（全工程の憲法）

> 本書は SCSCハイブリッド工程の**工程05〜13すべてが従う共通規律**である。
> 各工程プロンプトは本書を前提とし、重複する規定を個別には書かない。
> AIに渡す際は、各工程プロンプトの冒頭に本書を添付するか、`【共通規律】C1に従うこと` と明記して同時に貼り付ける。

---

## 0. 前提となる2階層モデル（最重要）

この工程体系は**2つの層**に分かれている。工程05〜13はすべて**第1層**の作業であり、**第0層の決定を再判定してはならない**。

| 層 | 誰が・いつ | 何を決めるか |
| :-- | :-- | :-- |
| **第0層｜テンプレ設計** | 人間が、業種・紹介区分ごとに**1回だけ** | 型A → 型A'（エコマド用等）を組む。**ブロックの順序・構成・TOP型・CVページ数**をここで確定する |
| **第1層｜案件充填** | 工程05〜13が、**案件ごとに** | 確定した型A（型A'）を受け取り、**中身を入れる**。順序・TOP型・ブロック選択は継承する |

### 第1層で許される自由（これ以外は禁止）

1. シートの「代用できるコンテンツ1〜3」列からの差し替え
2. シートの「利用可能パーツ2〜4」列からのパーツ変更
3. 案件事実（社名・数値・固有名詞・訴求文言）の充填
4. 可変2ページの**表示名**調整（後述）
5. 事業数・USP数に応じた詳細タブの増減
6. 公開ブロッカーの起票
7. 上記1〜2で足りない場合の**列外逸脱の起票**（承認を経るまで確定しない）

### 第1層で禁止される判断

- ブロックの**順序**変更（型Aの心理段階の並びを崩す）
- TOPの**型**（ダイジェスト／ハイライト）の再判定
- 型Aに存在しないブロックの**無断**追加
- デフォルト固定ページの改名（後述）

> **なぜこの分離が必要か**：過去案件では、第0層で決まっているはずのTOP型を案件側で再判定した結果、後工程の確定情報（施工事例ページの有無）によって判定が覆り、手戻りが発生した。第1層で判定させなければ、この種の揺れは構造的に起きない。

## 1. ページの改名規律

### 1-1. 完全固定（3ページ）── ページ名もディレクトリもAIは変更しない

| ディレクトリ | ページ名（この表記のまま使う） |
| :-- | :-- |
| `/privacy-policy/` | プライバシーポリシー |
| `/sitemap/` | サイトマップ |
| `/compliance/` | 反社会的勢力に対する基本方針並びにコンプライアンス指針 |

- 平易化・言い換え・短縮を**禁止**する（例：「サイトのご利用について」への変更は不可）。
- ディレクトリを `/terms/` 等に変更することも**禁止**する。
- 担当者が明示的に指定した場合のみ変更してよい。その場合は変更理由を記録する。

### 1-2. 事業形態で可変（2ページ）── **スラッグ固定・表示名のみ**調整可

| ディレクトリ（**変更不可**） | 標準表示名 | 調整の例 |
| :-- | :-- | :-- |
| `/company/` | 会社情報 | 個人事業主 → 「◯◯について」「事業者情報」等 |
| `/company/message/` | 代表挨拶 | 個人事業主 → 「◯◯のごあいさつ」等 |

- 変更してよいのは**サイトマップ掲載名・ナビ表記のみ**。ディレクトリ（スラッグ）は `/company/` `/company/message/` のまま固定する。
- 理由：URLを事業形態で変えると、後日の増設・移行時にリダイレクト管理コストが発生するため。

### 1-3. 施工事例のディレクトリ

- **`/case/` に統一**する。`/projects/` `/voice/` は使用しない。
- シートの `$article_code` とディレクトリが一致していることを検査する（過去に不一致の実績あり）。

## 2. 事実と証拠の規律

1. **証拠範囲の絶対**：数値・実績・資格・年数・保証・対応範囲は、統合版コンテキスト（工程04出力）および提供素材に**実在するものに限る**。存在しない事実を書かない。
   - 実在の判定先は **統合版コンテキスト S14「事実・数値台帳」**である。台帳に無い数字・年数・実績・資格・地域を、サイト上に記載してはならない。
   - 台帳の **「原文表記」を改変しない**（例：「2,300件」を「約2300件」にしない）。使用時は台帳のNo.を併記する。
   - 公開可否が `要確認` の事実は、**確認が済むまで使用不可**とする。
   - 台帳に必要な事実が無い場合、創作せず「S14に該当なし」として担当者へ差し戻す。**数字の無い設計で成立させることが正しい。**
2. **不明は「要確認」**：情報がない項目は推測で埋めず `（要確認：理由）` と明記する。空欄放置も禁止。
3. **推定は明示**：コンテキストから論理的に導いた解釈には `（推定）` を付し、何を根拠に導いたかを併記する。
4. **迷ったら弱める**：表現に迷う場合は、主張を**弱める方向**で解決する。誇張方向の解決を禁止する。
5. **誇大表現の禁止**：「No.1」「最安」「必ず」「完全」等は、コンテキストに客観的根拠が明記されている場合を除き使用しない（景品表示法）。

## 3. 逸脱の起票

型Aシートの列（代用コンテンツ1〜3／利用可能パーツ2〜4）で対応できない場合のみ、**逸脱として起票**する。黙って型A外のものを作ることを禁止する。

### 起票フォーマット

```
【逸脱起票 No.__】
対象：{タブ名} / {ブロック行} / {ブロック名}
やりたいこと：（1文）
なぜ列内で対応できないか：（代用列1〜3・パーツ列2〜4を検討した結果を1行ずつ）
コンテンツの意図：（この要素が果たす戦略的役割。パーツ選定の判断材料になる粒度で）
受けパーツ候補：（C3パーツ索引で照合した結果。該当なしの場合は「索引に該当なし＝新設アラート」）
影響範囲：（文字量・画像点数・他ブロックへの波及）
```

> **なぜ意図の記載が必須か**：逸脱の許容条件は「①コンテンツの意図がコンテキストに正しく記載されている ②適切なパーツが設置される」の2つである。意図が書かれていない逸脱は、パーツ選定を担当者の勘に依存させ、属人化を生む。

## 4. 公開ブロッカーの起票

「実装はできるが中身が空」になる箇所を、設計時点で洗い出す。

### 対象の例

- 施工事例ページを立てるが、掲載できる実績が0件
- お客様の声ブロックがあるが、素材提供が「不可」
- LINE導線を設計したが、公式アカウントか個人IDか不明（一斉配信の可否が変わる）
- 補助金の金額を訴求するが、制度名・年度・上限の一次確認が未完了

### 起票フォーマット

```
【公開ブロッカー No.__】
対象ページ／ブロック：
不足しているもの：
公開までに必要な条件：（例：施工写真を最低3件、各プラン1件以上）
条件未達で公開する場合の代替：（例：当該ブロックを非表示にし、◯◯へ差し替え）
```

## 5. 出力の共通ルール

1. **表形式を保つ**：各工程の出力フォーマットの列構成を変更・追加・削除しない。案件別一括生成シートへそのまま転記できることが要件である。
2. **タブ名・行番号を明記する**：シートのどこに書き込むかが特定できない出力を禁止する。
3. **検査値を併記する**：文字数制限のある項目は、必ず実測値を併記する（推測値・未記入を禁止）。
4. **省略記法の禁止**：「同上」「以下同様」等で行を省略しない。全件を明示的に書く。

---

## 6. 全工程共通の禁止事項

- 型A（型A'）シートが未添付の状態で作業を開始すること → **中断し、添付を要求する**
- 統合版コンテキスト（工程04出力）が未添付の状態で作業を開始すること → 同上
- 第0層の決定（順序・TOP型・ブロック構成）を第1層で再判定すること
- 完全固定3ページの改名・ディレクトリ変更
- 可変2ページの**スラッグ**変更
- 代用列・パーツ列を確認せずに独自のコンテンツ・パーツを当てること
- 逸脱・公開ブロッカーを起票せずに黙って処理すること
- コンテキストに存在しない事実（実績数値・資格・受賞歴）の創作
- 出力フォーマットの列構成の改変
